## 目的

對 `concepts.jsonl` 裡每個概念的 `relations[].context` 原始句子，判斷其
`relation_type`，補上 `relation_type` 與 `confidence` 兩個欄位。輸出的
`relations` 陣列格式：

```json
{
  "tail": "上游概念 UUID.概念名，或 null",
  "context": "原始句子",
  "relation_type": "見下方六選一",
  "confidence": "high | medium | low"
}
```

本規範描述的判斷規則是**決定性的（deterministic）**——同一份輸入，任何人
（或任何 AI）依此規則執行，理論上應該得到相同輸出。這是刻意設計：關係
「抽取」與「分類」都應該是可重現的，不依賴誰來執行、依賴的心情或當下的
語意判斷。

---

## relation_type 六種分類

| relation_type | 對應符號 | 語意 |
|---|---|---|
| `derives_from` | `←` `⇒` | 左邊由右邊的公設/概念推導而來 |
| `leads_to` | `↝` | 左邊發生會導致右邊發生（因果鏈） |
| `falsified_by` | `⊗` | 右邊的觀察會推翻左邊的命題 |
| `mutually_exclusive_with` | `⊕` | 多個選項互斥且窮盡（封閉分類） |
| `implies` | `→` | 若左邊成立則右邊成立（邏輯條件） |
| `references` | 無符號，或只是提及另一個概念的名字 | 純引用，非推導/因果關係 |

## 判斷規則（依序執行，符合第一條就停）

### 規則 1：符號優先權

依下列順序檢查 `context` 是否包含對應符號，符合就採用該分類：

```
⊗ > ⊕ > ↝ > ← > ⇒ > →
```

若同一句 `context` 裡出現**兩種以上不同符號**，仍依上述優先權取一個分類，
但 `confidence` 降為 `medium`（代表這句話語意上可能混合了多種關係，
建議人工複核，尤其是多步驟因果鏈被壓縮成一句話存放的情況——見「已知限制」）。

若同一句只出現**同一種符號、多次**（例如一整條因果鏈 `A ↝ B ↝ C ↝ D`），
仍視為單一符號類型，`confidence` 為 `high`。

### 規則 2：純文字推導句型（無符號時的 fallback）

若規則 1 找不到任何符號，檢查 `context` 是否符合手冊 C5.6a 規定的推導
來源格式：

```
正則表示：從.+?推出
例：（從 40a22ff8-....死亡律 推出）
   （從 P3 + 信號容器 + P4 推出）
```

符合的話，分類為 `derives_from`，`confidence` 為 `high`。

### 規則 3：純引用 fallback

規則 1、2 都沒有命中：

- 若 `tail` 不是 `null`（代表句子裡有明確的 UUID 上游引用），分類為
  `references`，`confidence` 為 `high`
- 若 `tail` 是 `null` 且沒有任何符號、也沒有推導句型，分類為
  `references`，`confidence` 為 `low`（這種情況代表這句話為什麼會被
  抽取進 relations 不太確定，建議人工檢查是否為抽取階段的誤判）

## confidence 欄位的語意（重要，避免誤讀）

`confidence: high` 代表**符號/句型判讀清楚、規則命中明確**，不代表
「語意上保證正確」。規則本身是機械式的符號比對，不是語言理解——如果
`formalization.md` 寫作時符號用法本身就不精確（例如作者把 `↝` 和 `→`
混用），規則會忠實反映這個不精確，`confidence: high` 不會幫忙抓出來。

真正需要人工複核的優先順序：
1. `confidence: medium`（多符號重疊）
2. `confidence: low`（規則完全沒命中，退到最保守的猜測）
3. 抽樣抽查幾筆 `high`，確認符號用法本身在原文裡是否精確

## 已知限制（v1.1 尚未處理，留待未來版本）

1. **顆粒度問題**：一整條多步驟因果鏈（如 `A ↝ B ↝ C ↝ D`）目前整句存成
   一筆 `relations`，只給一個 `relation_type`。如果未來需要逐步驟拆解
   （例如做推理鏈評測，需要知道 A→B 這一步跟 C→D 那一步分開驗證），
   需要在**抽取階段**（`DatasetExporter.java`）就把因果鏈拆成多筆，
   而不是在分類階段處理——分類階段拿到的已經是整句合併後的 context，
   無法再往回拆。
2. **符號誤用不會被抓出來**：見上方 confidence 說明。
3. **`references` 桶仍是異質的**：目前 `tail` 非 null 的 references（明確
   UUID 引用）和 `tail` 為 null 的 references（不確定為何被抽取）語意
   上不同，但都歸在同一個 relation_type，未來可考慮拆成兩種標籤。

## 執行方式（給人或給 AI 都適用）

**給 AI（例如貼給 Claude）**：把本文件連同 `concepts.jsonl` 一起貼上，
要求依此規則逐筆判斷，輸出格式不變、只新增 `relation_type` 與
`confidence` 兩個 key，不更動其他欄位，不用輸出說明文字。

**給人（或寫成腳本自動跑）**：規則 1、2、3 都是正則表示式等級的判斷，
可以直接寫成 Python/Java 腳本，不需要語言模型介入。如果專案規模持續
擴大、需要重複執行，建議實作成腳本，比每次貼給 AI 更快、更省成本、
結果保證一致。本規範的存在目的就是讓「用 AI 做」和「寫腳本做」兩種
執行方式，依循同一套規則，輸出應該一致。
