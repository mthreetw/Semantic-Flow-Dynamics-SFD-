# 群星規範——說明文件

*框架設計決策與操作流程。供作者閱讀，不進入 AI 任務 context。*

---

## 一、為什麼需要這套東西（原 §0）

### 問題

框架有十幾篇互相引用的論文，而且還在演化。改了一個概念的定義，哪些下游論文的引用斷了？靠人腦記不住。漏了就是內部矛盾，而且不會立刻發現。

### 方案

把論文的概念結構翻譯成 Java 型別。改了概念，編譯器自動告訴你哪裡斷了。

### 為什麼是 Java

- **OWL / 本體論：** 能推理，但要學新語言，殺雞用牛刀。
- **Lean / Coq：** 最嚴格，但學習成本天文數字，而且論文大量內容不可形式化。
- **Prolog / 邏輯語言：** 解決的是「從已知推未知」，但你要解決的是「改了舊的哪裡斷了」，這是兩個不同的問題。
- **Excel / 概念表：** 完全靠人，漏了沒人提醒。
- **Java：** 作者是碼農，工具鏈已經會了。record 是不可變結構體，天然適合表達概念定義。選 Java 不是因為它最好，是因為它成本最低。

不需要學新語言。邏輯自洽性和自然語言分析交給 AI——AI 直接讀中文論文，不讀 Java。Java 只做 AI 做不好的事：跨論文引用追蹤和改動傳播。

### 三層分工

| 層 | 功能 | 載體 | 做什麼 | 做不到什麼 |
|---|---|---|---|---|
| 自然語言 | source of truth | 論文（.md） | 承載完整論證：定義、推理、證據、邊界 | 有歧義，不報錯，改了不通知 |
| 形式邏輯 | 結構壓縮 | 獨立形式化文件（.md） | 消除歧義，壓縮結構，供 AI 跨論文比對 | 壓縮必然有損，丟掉上下文和隱含前提 |
| Java | 概念登記簿 | Java 文件（.java） | 改了就報錯 | 只查存在性，不查語意正確性 |

每篇論文產出四個文件：論文、英文翻譯、形式化文件、Java 文件。

### 三層檢查分工

| 檢查者 | 檢查對象 | 檢查內容 |
|---|---|---|
| 多 AI + 手冊約束 | 形式化文件 | 格式合規、完整性、內部一致性 |
| 編譯器 + ArchUnit | Java 文件 | 概念存在性、結構變化、引用斷裂 |

### Java 層只做三件事

1. **record 表達概念**——概念存不存在
2. **field 表達上游包裝**——這個概念是否依賴直接上游概念
3. **field 型別表達引用**——改了被引用的概念，引用處報錯

其他所有關係（包含、蘊含、推導、封閉分類、衝突、循環、歸零……）留在自然語言和形式邏輯層。Java 不表達它們，因為表達了編譯器也不檢查。

### 一句話邊界

**Java 層是一本會自動報錯的概念登記簿，不是邏輯引擎、不是推理系統、不是知識圖譜。**

### 危險與邊界

多 AI 交叉審核的系統性風險：所有 AI 的訓練數據高度重疊，偏差方向可能相關。如果錯誤落在所有 AI 的共同盲區，多 AI 會一致放過。形式化的價值在於提高下界，不在於消除盲區。

## 二、倉庫目錄結構（原 §2.1）

所有論文存放在同一個 Git 倉庫中。資料夾名稱使用 `paper_` 前綴加上 UUID（`-` 替換為 `_`），與 Java package 名稱一致。每個資料夾內含固定四個文件：

```
[倉庫根目錄]
  └── src/main/java/
        ├── paper_40a22ff8_9d90_4e1e_82f6_1fd80917c139/    （SFD——基礎論文，持有原語和公設）
        │     ├── 語意流動力學.md                           （論文）
        │     ├── Semantic Flow Dynamics.md                 （英文翻譯）
        │     ├── formalization.md                          （形式化文件）
        │     └── Concepts.java                             （Java 文件，全部空 record）
        ├── paper_a1b2c3d4_e5f6_7890_abcd_ef1234567890/
        │     ├── 宗教正反饋循環與現代化碰撞動力學.md
        │     ├── Religious Positive Feedback Loop and Modernization Collision Dynamics.md
        │     ├── formalization.md
        │     └── Concepts.java
        └── ext/                                            （外部著作存根，不進入正式審核流程）
              └── ext_aaa_bbb_ccc_ddd_000000000000/        （如：盧曼《社會系統》）
                    ├── formalization.md                    （極簡：來源、詮釋者、概念清單）
                    └── Concepts.java                       （全部空 record）
```

SFD 在結構上與其他論文完全相同。它的特殊性在語意層：公設和原語定義在這裡，框架的基本世界觀在這裡。所有論文都以 SFD 為直接或間接上游。

外部存根只記錄詮釋者對外部著作的概念理解，不走形式化審核流程。外部著作文字不會改，但詮釋可能更新——更新存根後，引用該存根概念的論文 Java 檔案會崩潰，傳播鏈照常運作。外部存根的 formalization.md 格式：

```
來源：作者,《著作名》, 出版年
詮釋者：[你]
詮釋日期：YYYY-MM-DD

## 概念清單

自我增長 (Autopoiesis)：系統持續再生產自身構成要素的過程
結構耦合 (Structural Coupling)：兩個自我增長系統之間穩定的刺激-回應關係
```

JSON 只有 `exports`，無 `references`（不追蹤外部著作之間的依賴）：

```json
{
  "exports": ["自我增長", "結構耦合"]
}
```

## 三、完整流程（原 §10）

### 3.1 論文註冊（寫作之前）

1. **生成 UUID（v4）**——決定 package 名和資料夾名，不可更改
2. **定英文標題**——放入 Javadoc 元數據，不可更改。中文標題可以後面改
3. **寫論文**——概念標注分三種：本篇原生概念 `[X](X)`，框架內上游概念 `[X](UUID.X)`，外部存根概念 `[X](ext:UUID.X)`；文末放 JSON 參考文獻

### 3.2 形式化（論文完成後，AI 執行）

```
論文（.md，文末含 JSON 參考文獻）
  → AI 讀論文手冊
  → AI 讀 JSON references，拉取所有上游形式化文件
  → 發現論文標記或 exports 問題 → 列問題，等作者修正論文 → 修正後繼續
  → AI 讀形式化手冊
  → AI 生成形式化文件（受形式化手冊約束）
  → 待決項非空 → 暫停，等待作者裁決 → 清零後繼續
  → 多 AI 交叉審核（逐條檢查形式化手冊所有 C 編號約束）
  → 審核不通過 → 打回重新生成
  → 審核通過 → AI 讀 Java 手冊，從形式化文件翻譯為 Java
  → 編譯 + ArchUnit
  → 輸出四個文件
```

詳細步驟：

1. **讀上游**——先讀 SFD 形式化文件（`paper_40a22ff8_9d90_4e1e_82f6_1fd80917c139/formalization.md`），錨定原語語意。然後按論文文末 JSON 的 references 逐條拉取：無 `ext:` 前綴者路徑為 `paper_UUID_/formalization.md`，有 `ext:` 前綴者路徑為 `ext/ext_UUID_/formalization.md`。只讀形式化文件，不讀上游論文的自然語言，不讀任何 Java 文件。讀取每份框架論文的引用列表時，檢查是否包含本篇 UUID（直接循環），或從已讀取的上游中可辨識出更長的引用環（遞移循環）；發現循環即中止並報告路徑，等待作者修正 `references`（見論文手冊 C4.1i）。外部存根不做循環檢查
2. **讀入新論文**——識別概念和結構。`[X](X)` 是本篇原生概念，`[X](UUID.X)` 是框架內上游概念，`[X](ext:UUID.X)` 是外部存根概念。本篇 exports 列出本篇原生概念，references 列出直接上游 UUID（含 ext: 前綴者）
3. **提取概念**——每個概念一個 record。本篇原生概念翻譯為空 record；包裝直接上游概念者翻譯為含單一 field（名稱為「上游」）的 record
4. **提取引用**——跨論文引用通過 field 型別指向被引用的 record
5. **生成形式化文件**——用形式化手冊的符號表寫出完整的形式化表示，獨立於論文，能脫離論文閱讀。框架內上游概念使用 `UUID.概念名` 格式，外部存根概念使用 `ext:UUID.概念名` 格式。推導鏈的粒度與論文一致——論文中存在跳步時，不可自行補充，必須標記 `[論文跳步]` 並列入待決項。文件結尾附概念摘要區塊（含英文翻譯）和待決項區塊
6. **待決項閘門**——待決項非空時暫停，等待作者裁決。AI 根據裁決修改形式化文件，清零後進入審核
7. **審核**——多 AI 交叉審核（見形式化手冊第四節），全部通過後進入 Java 翻譯
8. **翻譯為 Java**——翻譯概念（record）、上游包裝（單一 field 名稱為「上游」指向直接上游 record）。所有其他關係（包含、蘊含、推導、封閉分類、收窄等）留在形式化文件，不翻譯到 Java。UUID 機械式轉換為 package 名。SFD 原語通過 import SFD package 使用，不在本篇重建
9. **編譯**——javac 編譯整個項目，零錯誤才算通過
10. **結構測試**——ArchUnit 四項測試全部通過
11. **輸出**——四個文件：論文（`中文標題.md`）、英文翻譯（`English Title.md`）、形式化文件（`formalization.md`）、Java 文件（`Concepts.java`），存放在 UUID 資料夾中

### 3.3 更新與維護

- 論文修改後，重新執行 3.2 全部步驟
- 四個文件一起 commit
- UUID 不變，Git commit history = changelog

### 3.4 手冊版本變更後重跑

本框架維護三份獨立的手冊版本號，分別追蹤各自的變更。形式化文件頭記錄三個版本號，表示生成時使用的各手冊版本。

**論文手冊版本升級**：影響論文標記規則（C4.x）。已生成的形式化文件和 Java 文件不受影響，但受影響論文的標記需檢查修正。

**形式化手冊版本升級**：影響形式化格式或約束（C5.x、C8.x）。已有形式化文件需重新生成並審核。判斷標準：這次改動會不會讓形式化文件輸出不一樣。

**Java 手冊版本升級**：影響 Java 產出（C6.x、ArchUnit 測試）。所有既有論文必須重跑翻譯步驟。判斷標準：這次改動會不會讓 Java 輸出不一樣。大版本升級：上游概念結構有改的，先跑上游；其餘情況任意順序。依優先級逐步追趕即可，但版本落後的形式化文件不得作為新論文的上游引用。

## 四、編譯檢查能力與限制（原 §11）

### 能查的
- 概念是否存在（record 在不在）
- 跨論文依賴是否斷裂（被包裹的上游 record 消失，報錯）
- package 之間是否循環依賴（ArchUnit 測試一）
- record 是否最多一個 field、來自不同的 paper_ 或 ext.ext_ 包、且 field 名為「上游」（ArchUnit 測試二，同時覆蓋原測試二的同包自引用場景）
- record 中是否存在禁止的方法或 compact constructor 邏輯（ArchUnit 測試三）
- 每個 paper_ package 是否恰好一個外層 class 且命名為 Concepts（ArchUnit 測試四）

### 查不到的
- 概念的語意是否正確（編譯器不懂自然語言）
- 概念是否完整登記——由 AI 形式化步驟負責，AI 依 C4.1h 主動掃描
- 上游語意是否變化——語意變化必然導致形式化變化，形式化變化必然導致 Java 變化，Java 變化導致下游編譯崩潰，傳播鏈封閉
- 蘊含、推導、衝突等邏輯關係是否成立——靠 AI 審核

**編譯器只查存在性和依賴鏈，語意正確性靠 AI 讀自然語言論文和形式化文件。**

## 五、版本管理（原 §12）

- 論文是 source of truth
- 形式化文件和 Java 文件是生成產物，不手動維護
- 每次論文修改後重新生成形式化文件和 Java，重新編譯 + 跑結構測試
- 四個文件一起 commit，用 Git 管理，commit history = changelog
- 概念語意變化必須重跑形式化，形式化變化必然帶動 Java 變化，下游編譯崩潰後由人決定處理方式，在同一次 commit 中完成

## 六、改版說明

### v6.0（v5.1 → v6.0）

### 主要改動

**廢除 core 包，原語和 Postulate 移入 SFD：**

v5.1 及以前設有獨立的 `core` package，持有 `Postulate.java` 和各原語 `.java`（時間、空間、個體、刺激、死亡、規則）。

v6.0 廢除 `core` package。設計理由：
- 框架的每篇論文都引用 SFD（語意流動力學），SFD 本身就是所有論文共同的基礎
- 原語的語意聲明（「個體是預理論的」等）就寫在 SFD 的公設中，概念上屬於 SFD
- 設置獨立的 core 只是添加一個多餘的抽象層，在 Java 型別追蹤層沒有帶來任何額外能力

v6.0 改動：原語和 Postulate 定義在 SFD 的 `Concepts.java` 中。其他論文 import SFD package 即可使用。ArchUnit 原有的測試七（「core 禁止引用 paper_」）隨之刪除，縮減為六項測試。

**文件拆分（一份 → 四份）：**

原規範為單一文件，所有任務的 AI 都讀完整文件，導致 context 浪費。

v6.0 拆為四份：
- **論文手冊**：論文寫作和標記規則
- **形式化手冊**：形式化文件格式和審核規則
- **Java 手冊**：Java 翻譯規則和結構測試
- **說明文件**：設計決策和操作流程（本文件，供作者閱讀）

每份手冊攜帶獨立版本號，任務 AI 只讀對應手冊，節省 context，更新後只需重跑受影響的任務。

**版本號系統：**

原版本號為單一字串（如 `v5.1`）。v6.0 改為三個獨立版本號，形式化文件頭改為三行：

```
論文手冊版本：v6.0
形式化手冊版本：v6.0
Java 手冊版本：v6.0
```

**移除「使用原語」欄位：**

原形式化文件頭有「使用原語」欄位，用於區分「本篇空 record」和「core 原語」。core 廢除後，原語成為 SFD 的普通框架內引用概念，通過標準 UUID 引用機制處理（如 `40a22ff8-9d90-4e1e-82f6-1fd80917c139.個體`），欄位隨之移除。

**重跑要求：**

Java 手冊變動影響 Java 產出（Postulate 引用路徑、field 型別白名單），所有既有論文需重跑 Java 翻譯步驟。形式化文件頭格式也有變動（三版本號、移除使用原語欄位），需重新生成形式化文件。

### v6.1（v6.0 → v6.1）

**概念來源分類簡化：**

v6.0 的三類概念（本文原生、框架內引用、外部詮釋）合併為一類——所有概念均為本篇原生概念。框架內論文的概念和框架外文獻的概念，處理方式完全相同：都是本篇定義一個概念，定義裡可以包含任何來源的上游概念，UUID 是來源標記，不區分框架內外。

**相應刪除：**
- 論文正文的 `[X](UUID.X)` 標注格式（所有概念一律 `[X](X)`）
- 形式化文件頭的「外部詮釋」欄位
- 同名聲明（同名概念直接禁止）
- C4.3c、C4.3d、C5.1g/h/i（外部詮釋相關約束）

### v6.3（v6.2 → v6.3）

**論文頭部：**

論文 .md 文件新增 YAML 頭部，包含 `uuid` 和 `last-modified`。UUID 與資料夾名稱一致，論文本身因此具有自我識別能力。新增 C4.0a/b/c。

**外部存根（ext/）：**

引入外部著作存根機制，存放在頂層 `ext/` 資料夾，Java package 為 `ext.ext_UUID`。外部存根不走正式形式化審核流程，只記錄詮釋者對外部著作的概念理解。`references` 中以 `ext:UUID` 格式標記外部存根依賴。

**行內引用標記恢復：**

v6.1 刪除了 `[X](UUID.X)` 格式，導致正文失去來源資訊。v6.3 恢復三種標注格式：本篇原生概念 `[X](X)`、框架內上游概念 `[X](UUID.X)`、外部存根概念 `[X](ext:UUID.X)`。C4.2a/b 更新，新增 C4.2c/d。

**Java 手冊升至 v6.4：** ArchUnit 測試二擴展，field 型別允許來自 `ext.ext_` 包。

**重跑要求：** 論文需補加文件頭並更新行內標注格式；Java 手冊變動需重跑所有論文的 Java 翻譯步驟。

**Java 層極度簡化：**

v6.1 的 Java 層仍保留了包含關係（record 有多個 field）。v6.2 確立：

- record 只有兩種：空 record、或恰好一個 field 名稱為「上游」指向直接上游 record
- 封閉分類（sealed interface）完全移出 Java 層，留在形式邏輯層
- 概念的內部組合不在 Java 表達，Java 只追蹤「這個概念存在」和「這個概念依賴哪個直接上游概念」
- Postulate 變為空 record，不再持有 String 內容

**傳播鏈封閉性確認：**

語意變化 → 形式化變化 → Java 變化 → 下游編譯崩潰。這條鏈是封閉的。上游改了語意必然改形式化，形式化改了必然改 Java，Java 改了下游必然崩潰。沒有靜默失效的路徑。

**重跑要求：** 所有既有論文需重跑 Java 翻譯步驟（record 結構全部變化）。
